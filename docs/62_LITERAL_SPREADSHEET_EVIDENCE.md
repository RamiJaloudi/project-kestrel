## Additional bounded formats — 24 November 2026

[IMPLEMENTED / LOCAL DEMO] New intake accepts literal XLSM XML without executing or converting macros. Original VBA/ActiveX/embedded bytes remain in the immutable original; their retained metadata contains only paths and hashes. Sheet names/states, including empty tabs, hidden rows/columns, comments and defined names remain evidence. Hidden/opaque new-format content requires declared clean-team handling and current named membership for an explicit source scope before firm intake. Halden uploads require declared clean-team handling and the existing named pricing membership; firm acceptance remains a separate controlled source intake. The client content heuristic cannot weaken an explicitly declared clean-team restriction. Existing XLSX and tracker upload contracts are preserved.

New XBRL and XML XHTML iXBRL intake retains expanded concept names, entity identifiers/schemes, context periods and dimensions, unit numerators/denominators, source accuracy declarations, nil status, raw numeric text and Decimal values. iXBRL values retain explicit sign, scale and transformation. This is evidence extraction, not taxonomy validation or financial/legal approval. No schema, taxonomy, linkbase, script or URL is fetched, and no XBRL formula/calculation network is executed. Each fact has a retained unit/offset for the existing reader and subsequent human financial capture; no relational approved fact is automatically created.

The supported iXBRL numeric subset uses strict decimal literals or the explicitly declared 2020 registry `num-dot-decimal`, `num-comma-decimal` and `fixed-zero` transforms. Grouped numeric lexical forms use conventional three-digit separators. Unsupported transforms, ambiguous grouping, fractions, tuples, target-document routing and exclude mappings fail explicitly. Nil is preserved as missing value, never converted to zero. XML trees, IDs, contexts, units, facts, nesting, digit lengths and text have fixed bounds; DTDs/entities, duplicate/dangling references and active XHTML elements are denied. The implementation follows the distinction between context, units and accuracy in [XBRL2.1](https://www.xbrl.org/Specification/XBRL-2.1/REC-2003-12-31/XBRL-2.1-REC-2003-12-31%2Bcorrected-errata-2013-02-20.html), explicit scale/sign in [Inline XBRL1.1](https://specifications.xbrl.org/work-product-index-inline-xbrl-inline-xbrl-1.1.html), and the named namespace in [Transformation Registry4](https://www.xbrl.org/Specification/inlineXBRL-transformationRegistry/REC-2020-02-12/inlineXBRL-transformationRegistry-REC-2020-02-12.html). It does not claim full standards conformance.

EML intake retains inert headers and bounded plain-text/HTML-text bodies, without rendering HTML or fetching remote content. Supported attachments stay staged inside the retained original message: names, size, MIME declaration, byte hash and `staged_not_ingested` state are recorded, while child contents are not silently added to the parent evidence corpus or ingested as sources. Attachments make the new email require scoped clean-team handling. An explicit attachment download can be manually submitted through normal separate-source intake; neither download nor staging creates a child source or approval.

`GET /api/v1/workflow/documents/{source_id}/attachments` lists current source-authorized staged metadata. `GET /api/v1/workflow/documents/{source_id}/attachments/{index}/download` additionally requires the canonical source `download` action, verifies the retained manifest and rechecks identity/policy snapshots before serving an attachment as `application/octet-stream`, with `nosniff` and `no-store`. Signing allows these read-only operations while the source and user remain authorized; lifecycle closure, source policy, walls and clean-team revocation continue to apply. Denied responses contain no MIME filenames. No download can recall an earlier saved copy.

EML rejects executable signatures, unsafe names/paths, archives, macro-enabled attachments, nested/external messages, unsupported parts and bounded-limit violations. Supported Office attachments pass the existing no-macro/no-external-link package guard; PDF attachments with actions, forms, annotations or embedded files are rejected. Limits are 3MiB raw/decoded message content, 100 MIME parts, depth10, 25 attachments, and 150,000 extracted characters. Legacy XLS/PST/OST/MSG remain explicitly unsupported (`415`) until an approved safe converter is selected. Parser bounds and inert extraction are not a substitute for production malware scanning and OS isolation.

The source reader presents XLSM cells as a read-only grid and retained metadata in its evidence pane. XBRL/iXBRL/EML use escaped text evidence, with no HTML original viewer. Sanitized output omits retained hidden/opaque units; it reconstructs new text and never copies source macros, MIME attachments or XML/HTML objects.
